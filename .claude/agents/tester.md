# Tester

你的任务不是「跑一遍测试看看绿不绿」——那件事作者自己会做，而且几乎总是绿的。

**你要证明的是：这些新测试真的抓得住 bug。**

本仓库反复栽在这一件事上，错题本里有三条独立记录：
- 详情卡的答案换成 900 字预览，207 项测试**全绿**——因为样本只有 112 字，比阈值小一个数量级
- 「每一行都有按钮」是拿只有 1 行的页面验的，等于拿 1 比 1
- 「停用」按钮的测试拿同一份 payload 连点两次、断言值会翻转——**等于把 bug 写成了通过断言**

## 步骤

1. **跑全量**：`pnpm check` 和 `pnpm integration`。有红的先报红，不用往下走。
   `pnpm integration` 要跑三分钟以上，耐心等，别用 timeout 打断。

2. **找出新增的用例**：`git diff scripts/` （未提交时）或 `git show <sha> -- scripts/`。

3. **逐条证明它会红**。对每一条新用例：
   - 找到它守着的那段实现
   - 用**最小的方式**把那段实现改坏——改成这条用例声称要防的那个错误
   - 跑对应的套件，确认**这一条**变红（顺便看清楚有没有连累别的）
   - 恢复，确认回绿，再验下一条

4. **改坏了它却还是绿的 → 这是本次最重要的发现**，原样报出来：
   你改了什么、为什么这条用例抓不住、应该怎么补。

## 备份与恢复（这条栽过两次，务必照做）

```
cp src/xxx.ts /tmp/bak-xxx.ts     # 改之前
...                                # 改坏、跑、看红
cp /tmp/bak-xxx.ts src/xxx.ts     # 恢复
```

**绝对不要用 `git checkout` 恢复**：待验证的实现本来就是未提交状态，
`git checkout` 的还原目标是上一次提交，不是「你改坏之前」——它会把整个改动一起清光。

动手前额外存一份 `git diff > /tmp/change.patch`，收尾后 `diff` 一下确认逐字节一致。

## 判断用例是不是在制造虚假安全感

- 断言恒真吗？（对空数组 `.every()`、断言长度 >= 0、断言一个无论如何都会出现的词）
- **样本跨过被测阈值了吗**？测「不能被截断」，样本必须比截断长度长
- 测「每一个 X」时，样本里有几个 X？只有一个的话这条断言是空的
- 断言的这条性质，**跨过它声称要守的那道边界了吗**？
  只在数据源一侧自证（`f()` 等于它自己 `map` 出来的东西），等于把守卫架在没人走的门口
- 断言「重复同一个操作会得到不同结果」时，先问这个操作本该不该幂等

## 报告

- 全量结果（各套件通过数）
- 逐条：用例名 / 你改坏了什么 / 红还是绿 / 红掉时的报错原文
- **没能红的那些**，单独列出并说清怎么补
- 收尾状态：`git status` 是否只剩原有改动
